# Qwen3-VL 本地视觉复核设计

**日期：** 2026-08-04

**状态：** 已批准，分阶段实施

**实施授权：** 2026-08-05 用户指示继续自动照护风险识别开发；先实现纯确定性
风险核心，再接安全帧链路、M2 模型、证据与通知。任何阶段均不得宣称医疗监护
或无人照护能力。

**范围：** 现有小米 MJSXJ17CM、Intel i9 Mac 采集与告警、M2 Mac 本地
Ollama `qwen3-vl:8b` 视觉复核；USB 摄像头只预留适配器边界

## 1. 目标

在现有 `Baby Monitor Local Alpha` 的高清取流、Dashboard、截图和 ntfy
基础上，增加第一版完全本地的婴儿床视觉候选提醒闭环：

1. i9 从已经验证的 MJSXJ17CM `source` 流采集低频关键帧；
2. M2 使用 Ollama `qwen3-vl:8b` 复核连续画面；
3. i9 的确定性状态机判断持续时间、升级、恢复和告警；
4. 告警时在 i9 本地保留关键截图、事件前后短片和结构化记录；
5. 两台 Android 通过 ntfy 实时收到文字提醒，并通过 Tailscale 打开受鉴权的
   本地事件详情。

第一版只生成辅助照护候选，不判断呼吸、心率、血氧、窒息或其他医疗状态，
也不能替代成人持续照护。

## 2. 本次功能边界

第一版只处理以下六类结果：

- 面部持续不可见或疑似被被褥、玩具等遮挡；
- 明显趴睡候选；
- 婴儿离开床区候选；
- 成人介入，以及介入后风险是否解除；
- 摄像头断流或画面冻结；
- M2、SSH 隧道或 Ollama 不可用时的降级提醒。

本次不包含哭声、咳嗽、异常声音、温湿度自动读数、自动 PTZ、JoyAI、外部
大模型、云端视频分析或 USB 摄像头实际接入。声音后续使用独立音频检测链路，
不交给 Qwen3-VL。

## 3. 选定架构

```text
MJSXJ17CM source（2560×1440）
  ├─ 摄像头 microSD：全天循环录像
  └─ go2rtc（i9 loopback）
       ↓
i9 visual-review worker
  ├─ 内存帧环：960×540 JPEG，普通帧不落盘
  ├─ 画面冻结、断流等确定性健康检查
  ├─ 通过 127.0.0.1:11435 调用 M2
  ├─ 风险状态机、事件切片和本地证据
  └─ ntfy 文字告警
       ↓ 持久 SSH 本地端口转发
M2 127.0.0.1:11434
  └─ Ollama qwen3-vl:8b
```

采用独立 `visual-review worker`，不把采样或模型调用放进 FastAPI 请求处理器。
worker 或 M2 故障时，现有实时查看、microSD 录像、米家 App 和 Dashboard 仍可
独立工作。

拒绝把 Ollama 设置为 `0.0.0.0:11434`。M2 上的 Ollama 保持 loopback-only，
i9 使用 launchd 管理的 SSH 本地端口转发：

```text
i9 127.0.0.1:11435 → SSH → M2 127.0.0.1:11434
```

SSH 账户使用独立密钥、禁用密码登录，并通过 `authorized_keys` 限制为只允许
端口转发，不授予交互式远程 Shell。隧道断开必须自动重连，但不能使监控主服务
反复重启。

## 4. 摄像头适配器边界

视觉服务只依赖以下逻辑能力，不直接了解 Xiaomi URI、go2rtc 参数或未来 USB
设备编号：

```python
class AnalysisFrameSource(Protocol):
    def capture(self) -> AnalysisFrame: ...
    def health(self) -> FrameSourceHealth: ...
```

`AnalysisFrame` 包含单调时钟采集时间、带时区墙钟时间、宽高、受限 JPEG 字节
和非敏感来源代号。第一版 `Go2RTCFrameSource` 固定从 i9 loopback go2rtc 的
受控 `source` 取得画面；调用方不能提交 URL、流名称或 FFmpeg 参数。

以后接入 UVC USB 摄像头时增加 `AvFoundationFrameSource`，复用相同的帧环、
模型契约、状态机、事件存储和通知模块，不改变风险业务逻辑。

## 5. 采样与模型调用节奏

- 首次启用前必须在本地配置一个归一化 `bed_zone` 多边形；没有有效床区时视觉
  复核保持关闭并显示 `VISUAL_BED_ZONE_REQUIRED`，不得拿全房间画面试运行；
- 可配置多个归一化 `privacy_mask` 多边形，遮罩在任何模型传输或事件媒体写盘
  之前应用；
- 送入模型和事件缓存的画面固定为 `bed_zone` 外接矩形向四周扩展 15% 后的裁剪，
  再对落入裁剪范围的隐私区域填充纯黑；
- i9 每 2 秒取得一张分析帧，缩放到 `960×540`，JPEG 质量固定为 80；
- 内存帧环保留最近 40 秒，进程退出即消失；
- 每 10 秒选择最近四张、时间间隔约 2 秒的连续帧发起一次视觉复核；
- 同一时刻最多有一个模型请求；上次请求未结束时跳过本轮，禁止堆积；
- 单次请求总 JPEG 字节上限为 4 MiB，单帧上限为 1 MiB；
- 模型请求超时为 20 秒，超时后终止本次复核并进入健康计数；
- 出现画面显著变化或上一轮为 `watch/high` 时，可在最短 5 秒间隔后提前复核；
- 连续空闲时不提高到持续 3～5 FPS 模型推理。

第一版不把原始 2560×1440 帧持续发送到 M2。事件确认后可另取一张原生截图
作为本地证据，但不把该截图再次发送给模型。

## 6. Ollama 请求与结构化输出

i9 只调用固定 loopback 地址、固定模型和固定 API 路径。配置可选择关闭视觉
复核，但不能从 Dashboard 或 HTTP 请求中覆盖模型名称、基础 URL、系统提示词
或文件路径。

请求使用 Ollama 原生聊天接口、四张图片和固定 JSON Schema。温度设为 `0`，
禁止工具调用，输出只接受以下严格结构：

```json
{
  "schema_version": 1,
  "baby_visibility": "visible|partial|not_visible|uncertain",
  "face_visibility": "clear|partial|not_visible|uncertain",
  "posture": "supine|side|prone_candidate|upright|uncertain",
  "bed_state": "inside|outside_candidate|uncertain",
  "adult_presence": "present|absent|uncertain",
  "image_quality": "usable|dark|blurred|occluded|uncertain",
  "risk": "none|watch|high|uncertain",
  "reason_codes": ["face_not_visible", "prone_candidate"],
  "confidence": 0.82
}
```

`confidence` 必须位于 `0.0–1.0`，`reason_codes` 去重且最多五项，不允许额外
字段或自由文本。`reason_codes` 的唯一允许值为 `face_not_visible`、
`prone_candidate`、`outside_candidate`、`adult_intervention` 和 `poor_image`。
解析失败、枚举越界、额外字段、响应过大、模型名不匹配和 HTTP 异常统一计为
一次模型失败；原始模型输出不得写入普通日志或通知。

模型只描述可见画面，不推断疾病、危险原因、身份、情绪、性别或照护者意图。
提示词必须明确：看不清时输出 `uncertain`，不得为了满足格式而猜测。

## 7. 确定性状态机

Qwen3-VL 的单次输出不能直接发送高风险通知。i9 将输出归并为四种状态：

- `normal`：宝宝在床内，且未出现持续风险候选；
- `watch`：单次高风险候选、低置信度候选或图像质量不足；
- `alert`：候选满足连续性门限；
- `degraded`：摄像头、帧源、隧道或模型链路不可用。

规则固定如下：

| 条件 | 进入告警 | 恢复 |
|---|---|---|
| `face_visibility=not_visible` 且 `risk=high` | 两次有效复核，跨度至少 10 秒 | 两次 `clear`，跨度至少 10 秒 |
| `posture=prone_candidate` 且 `risk=high` | 两次有效复核，跨度至少 10 秒 | 两次非趴睡结果，跨度至少 10 秒 |
| `bed_state=outside_candidate` | 两次有效复核，跨度至少 10 秒 | 两次 `inside`，跨度至少 10 秒 |
| 连续 `uncertain` 或不可用画面 | 持续 60 秒发送检查画面提醒 | 两次可用结果 |
| 摄像头断流或冻结 | 持续 60 秒 | 连续 20 秒获得变化中的有效帧 |
| 模型、隧道或 Ollama 失败 | 连续 3 次或持续 60 秒 | 连续 2 次成功复核 |

`confidence < 0.70` 的风险结果只能进入 `watch`，不能累计为 `alert`。成人出现
时记录 `adult_intervention` 并抑制相同事件的重复通知，但不能单凭
`adult_presence=present` 将风险标记为恢复；必须重新看到对应的安全画面结果。

同一事件打开期间不重复发送相同级别通知。严重度升级时只发送一次升级消息，
恢复时只发送一次恢复消息。状态机重启后从本地事件快照恢复打开状态，但旧的
模型连续计数清零，避免用重启前的单帧直接触发告警。

## 8. 画面冻结与断流检测

断流、冻结和模型可用性由确定性代码判断，不依赖 Qwen3-VL：

- 采集超时、无效 JPEG 或源健康检查失败计为断流样本；
- 对床区隐私遮罩后的低分辨率灰度图计算感知哈希和亮度统计；
- 连续哈希近似相同本身不等于冻结，因为婴儿可能静止；
- 只有帧时间戳前进但编码内容、噪声统计和关键元数据持续完全不变 60 秒，才生成
  冻结候选；
- 冻结候选触发后通过重新建立一次受控帧源连接复核，仍不变才告警；
- 夜间静止场景、全黑画面和固定温湿度表不能单独形成冻结结论。

## 9. 事件证据、切片和保留

MJSXJ17CM 的 256GB microSD 继续作为全天循环录像主来源。i9 不新增 72 小时
连续录像，也不永久保存普通分析帧。

i9 维护至少 40 秒的短分片环形缓存：

- `watch` 只记录结构化事件，不落盘视频；
- 普通确认事件保存触发前约 20 秒、触发后约 60 秒；
- 高风险确认事件保存触发前约 30 秒、触发后约 120 秒；
- 每个确认事件保存一张原生关键截图、一个短片和状态机审计记录；
- 事件仍在持续时不重复生成多个相同短片，升级时扩展同一事件证据；
- 视频导出失败不能阻塞文字告警和状态记录。

普通事件媒体保留 7 天，高风险事件媒体保留 30 天；总媒体配额沿用 30GB。
超过配额时先删除最早普通媒体，再删除最早已恢复的高风险媒体；正在打开的事件
不得清理。结构化事件、确认和恢复记录沿用 V1 的一年保留期。

所有事件画面使用与模型相同的床区裁剪和隐私遮罩，只写入已被 Git 忽略的
`runtime/events/`；文件名使用随机事件 ID，不包含宝宝姓名、摄像头地址或
房间名称。

## 10. 通知与 Dashboard

ntfy 默认只发送：事件类型、严重度、发生时间、持续时间、当前链路状态和一个
经 Tailscale 打开的受鉴权 Dashboard 事件链接。公共或第三方 ntfy 服务不得
接收截图、视频、Xiaomi URI、局域网地址、模型原始输出或家庭身份信息。

Dashboard 增加：

- 当前视觉状态：正常、观察、告警或降级；
- 最近一次成功复核时间和非敏感模型健康状态；
- 打开事件、已恢复事件和人工“确认/误报”操作；
- 鉴权后的本地关键截图与短片；
- 明确的“辅助候选，不是医疗监护”提示。

如果以后部署完全自托管的 ntfy，媒体附件必须作为单独设计审批，第一版不自动
启用。

## 11. 配置与安全边界

新增配置必须进入现有严格 Pydantic 配置体系，并遵循 `extra="forbid"`。至少
包括：功能开关、固定模型名、loopback 模型网关地址、`bed_zone`、
`privacy_masks`、采样周期、超时、告警持续时间、证据保留和配额。生产默认值
与本规格一致；`bed_zone` 不设不安全默认值，必须由本机用户明确配置。

必须保持以下边界：

- Xiaomi URI、账号密钥、SSH 私钥和 ntfy Token 只保存在 i9/M2 本地；
- Ollama、go2rtc 和模型网关不得监听公网，也不得通过路由器转发；
- 模型请求只包含内存 JPEG，不包含录像路径或任意本地文件；
- 所有 HTTP 客户端禁用环境代理，防止本地画面意外进入代理；
- 日志只记录事件 ID、枚举、耗时、计数和安全错误码；
- 测试使用合成图、纯色图和程序生成场景，不提交真实宝宝画面；
- 外部大模型 API 地址与密钥不进入第一版配置契约。

## 12. 故障降级

- M2、隧道或 Ollama 离线：发送一次降级提醒，保留摄像头健康检查、实时查看、
  microSD 录像和本地事件环形缓存；恢复后发送一次恢复消息。
- i9 视觉 worker 崩溃：launchd 独立重启 worker，不重启 Dashboard 和 go2rtc。
- 摄像头离线：模型调用暂停，按 60 秒规则发送摄像头告警。
- ntfy 失败：事件与证据继续本地保存，按有界退避重试；不能阻塞采样。
- 磁盘不足：先执行事件保留策略；仍低于安全余量时停止新视频导出，但保留文字
  事件、实时告警和 microSD 录像。
- 模型延迟超过采样周期：保持单飞并跳过中间请求，不建立无限队列。

## 13. 实现组件

- `services/vision/frame_source.py`：帧源协议和受控 go2rtc 实现；
- `services/vision/frame_policy.py`：床区校验、15% 扩展裁剪和隐私遮罩；
- `services/vision/frame_ring.py`：有界内存帧环与四帧选择；
- `services/vision/ollama_client.py`：固定 endpoint、请求限制和严格响应解析；
- `services/vision/risk_state.py`：连续性、去重、升级和恢复状态机；
- `services/vision/worker.py`：采样、单飞调度和故障降级；
- `services/events/evidence.py`：关键截图、事件切片和配额；
- `services/notifications/ntfy.py`：文字通知和有界重试；
- `apps/api/alpha.py`：鉴权后的视觉状态和事件读取接口；
- `deploy/launchd/`：i9 worker 与受限 SSH 隧道服务；
- `tests/vision/`、`tests/events/`、`tests/notifications/`：合成数据和状态机测试。

USB 摄像头适配器、音频检测和温湿度读针不进入本次实现计划。

## 14. 定向测试与实机验收

所有生产行为遵循 TDD，先观察测试因缺少功能而失败，再写最小实现。自动测试
至少覆盖：

- 床区必填、归一化几何校验、15% 扩展裁剪、隐私遮罩先于传输和写盘；
- 帧环容量、采样间隔、四帧顺序、单帧与总字节限制；
- 固定 loopback endpoint、固定模型、代理禁用、超时和单飞；
- JSON Schema 的所有枚举、额外字段、自由文本、响应过大和不确定结果；
- 每类候选的两次确认、低置信度不升级、成人介入、去重、升级和恢复；
- worker 重启不沿用旧连续计数；
- 断流、冻结、夜间静止和全黑场景的区分；
- 普通/高风险切片窗口、导出失败不阻塞、保留顺序和打开事件保护；
- ntfy 负载不包含图片、视频、私网地址、原始模型输出或本地路径；
- M2 离线、模型超时、摄像头离线、磁盘不足和恢复路径；
- 现有 Dashboard 鉴权、实时画面、高清回退、截图、缩放和 PTZ 契约不回归。

i9 与 M2 实机门禁：

1. M2 在 loopback 上运行 `qwen3-vl:8b`，i9 只能经本地 SSH 隧道访问；
2. 白天、完全黑暗、蚊帐、成人介入、宝宝不在床内和模拟遮挡样本均形成记录；
3. 单次模型失败不报警，连续 3 次失败或 60 秒不可用只报警一次；
4. M2 正常复核的第 95 百分位响应时间不高于 8 秒；在该性能门禁内，确认风险
   于第二次有效复核后告警，目标延迟不超过 25 秒；
5. 正常恢复只发送一次，持续事件不产生通知轰炸；
6. 普通分析帧不落盘，事件媒体符合 20/60 秒或 30/120 秒窗口；
7. 断开 M2 后摄像头预览、microSD 录像和确定性健康告警继续工作；
8. 运行日志、ntfy 内容和 Git 状态不含家庭媒体、凭据、私网地址或模型原文；
9. 定向自动测试通过后运行一次现有全量 Python/Node 测试和 `git diff --check`；
10. 首次家庭夜间验收只记录候选和误报，不宣称可用于医疗或无人照护。

## 15. 明确不做

- 不移植 JoyAI，不运行其 webinfer、摘要模型或 delegate 体系；
- 不调用 OpenAI、DeepSeek、Kimi 或任何外部模型；
- 不让 Qwen3-VL 直接控制告警、云台、门锁或其他设备；
- 不把 Ollama、go2rtc、Dashboard 或摄像头端口直接暴露公网；
- 不把截图或视频上传到公共 ntfy；
- 不承诺识别窒息、呼吸暂停或任何医疗风险；
- 不在本次接入 USB 摄像头，但必须保持可替换帧源接口。
